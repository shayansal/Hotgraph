# KMS And Governance Hardening

Production deployments must not rely on plaintext data keys or custom local key
storage.

## Key Handling

Required model:

- KMS-managed master key per environment.
- Tenant-scoped data encryption keys generated by KMS or wrapped by KMS.
- Envelope encryption for event logs, snapshots, backups, and source stores.
- Key IDs stored in metadata; plaintext keys never stored in manifests, logs, or
  environment dumps.
- Automated rotation test for active and historical data keys.

## Secret Provenance

Allowed:

- Kubernetes Secret populated by an external secret manager.
- Cloud KMS/HSM reference.
- Local development `.env` only when `HOTGRAPH_DEV_AUTH_DISABLED=true`.

Forbidden:

- committed API keys
- plaintext production data keys in environment variables
- logging presented API keys or decrypted data keys
- ad hoc encryption not backed by a reviewed AEAD/KMS design

## Redaction Workflow

Redaction is represented as an append-only governance event. The system must
preserve auditability while preventing raw source or summary leakage.

Required checks:

- source retrieval honors redaction
- evidence packs omit redacted snippets
- summaries derived from redacted sources are invalidated or regenerated
- contradiction/path queries do not expose hidden assertion content
- restore drills preserve redaction state

## Tenant Isolation

Production query paths must treat tenant as a first-class access boundary.

Required checks:

- API principal tenant is attached before command validation.
- Query, path, evidence-pack, memory, and source retrieval apply tenant filters.
- Cross-tenant joins require explicit federation policy.
- Adversarial tests attempt direct ID access, summary leakage, path traversal
  leakage, and evidence-pack leakage.

Any confirmed cross-tenant leakage is a severity-1 incident.
